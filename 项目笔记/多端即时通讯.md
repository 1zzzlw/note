## `im-auth` — 用户注册、登录与多端会话

`im-auth` 管理账号登录、设备会话、凭据签发、刷新和退出。这章可以沿着一次登录来讲：**校验账号与验证码 → 为设备建立会话 → 签发双 Token → 网关校验业务请求 → 客户端收到 401 后刷新并重试**。

### 1. 多端登录：按用户和设备管理会话

如果只用用户 ID 存一份登录态，同一个账号在另一台电脑登录时，就可能覆盖原来的凭据。项目按 `userId + deviceId` 建立设备会话，每个设备保留一对当前有效的 Access Token 和 Refresh Token。

- **登录入口**：`POST /user/login` 在认证服务校验账号、密码和图形验证码。Electron 主进程生成并持久化设备 ID，登录时通过 `X-Device-Id` 传给后端。后端为这次登录生成 `sessionId`，把 `userId`、`deviceId`、`sessionId` 和随机 `jti` 写入 JWT。
- **同设备重登**：Lua 从该设备的会话 Hash 取出旧双 Token，删除其 Redis 用户信息索引，再写入新会话和新双 Token。不同设备拥有各自的会话键，因此 A 设备重登后，B 设备还能继续访问。
- **恢复与退出**：`/user/pendingLogin` 用已保存的 Refresh Token 恢复登录，主动构建新 `sessionId` 并轮换双 Token。`/user/logout` 根据 Refresh Token 定位并删除对应的设备会话及其双 Token 索引。缺少设备 ID 的新登录走 `legacy` 会话，以兼容旧客户端。

### 2. 双 Token 无感续期：401 后换发，再重试一次

Access Token 用于普通业务请求，JWT 有效期配置为 **1 小时**。Refresh Token 用于续期、恢复登录和退出等流程，JWT 有效期配置为 **365 天**。两类 Token 使用不同的签名密钥，实际能否使用还取决于 Redis 中的登录状态。

1. 登录成功后，服务在响应头 `Authorization` 返回 Access Token，在 `refreshtoken` 返回 Refresh Token。
2. 普通请求携带 Access Token。符合刷新条件的业务请求收到 401 后，Axios 拦截器调用 Electron 主进程的会话刷新方法。主进程拿当前账号的 Refresh Token 请求 `POST /user/refreshToken/{userId}`。
3. 网关先校验 Refresh Token，认证服务再核对 Token 对应的用户和当前会话。Lua 检查传入的旧 Refresh Token 是否仍是该设备当前有效的凭据，然后删除旧双 Token 并保存新双 Token。正常续期沿用现有 `sessionId`。
4. 客户端保存新双 Token。如果当前账号和会话版本仍匹配，原请求用新的 Access Token 自动重试一次。并发的 401 在同一账号会话内复用正在进行的刷新，刷新凭据失效时则结束对应的登录态。

**常见追问：并发收到 401 会怎么样？** 客户端把同一账号会话的刷新合并成一个进行中的请求。服务端用 Lua 在同一次执行里比较旧 Refresh Token 并完成轮换。第一条刷新成功后，后来携带相同旧凭据的刷新会被拒绝，避免旧状态覆盖新状态。

**常见追问：每次请求都续期，为什么 Access Token 还会过期？** 网关的 `EXPIRE` 延长的是 Redis 登录记录的存活期。JWT 的 `exp` 在签发时就固定了，到了这个时间，客户端还是要走刷新接口，拿一对重新签发的 Token。Refresh Token 的 365 天同样是 JWT 的配置上限，Redis 记录过期或被撤销后就无法继续刷新。

### 3. Redis 怎么用：会话索引、Token 校验和短期数据

| Redis 数据 | 类型 | 用途 |
| --- | --- | --- |
| `login:user:session:{userId}:{deviceId}` | Hash | 保存该设备当前的 `access`、`refresh` 和 `sessionId`，重登、刷新和退出可据此定位旧凭据。 |
| `login:user:Info:accessToken:{token}`、`login:user:Info:refreshToken:{token}` | Hash | 从请求携带的 Token 直接定位用户信息和 `deviceId`，供网关校验和传递用户上下文。 |
| `login:code:{验证码}`、`register:code:{手机号}` | String | 保存登录和注册验证码，有效期均为 2 分钟。 |
| `user:friend:list:{userId}` | Set | 登录时查询并预热好友 ID 集合，配置有效期为 2 分钟。 |

设备会话和双 Token 信息索引的 Redis TTL 当前均配置为 **36,000 分钟（25 天）**。项目还通过 Lua 处理旧版按用户维护的 Token 集合，以兼容已有登录数据。

**常见追问：已经校验了 JWT，为什么还要查 Redis？** JWT 校验能判断签名和过期时间。Redis 记录决定凭据当前是否仍有效，因此服务端可以主动撤销尚未到期的 JWT。设备索引支持按设备找到并撤销旧凭据，Token 索引支持网关从请求直接找到有效凭据对应的用户信息。这种做法让鉴权请求依赖 Redis 可用性，当前网关在 Redis 操作异常时返回 500。

### 4. AOP 登录限流：在业务执行前拦截超量并发

`POST /user/login` 标了 `@UrlLimit(keyType = LimitKeyType.IP)`。切面在 `@Around` 里读取请求，通过 `ConcurrentHashMap<String, AtomicInteger>` 为每个身份和 URI 维护一个实例内计数器。切面实际优先取 `UserHolder` 里的用户 ID，未登录时用客户端 IP，登录请求因此通常按 **IP + URI** 计数。

请求进来先加一，超过默认阈值 **30** 时抛出 `IPException`。放行的请求在 `finally` 里减一，每分钟还有一次清理计数表的任务。这个流程的设计意图是限制同时处理的登录请求。注解注释写着“每分钟最大请求次数”，但顺序完成的请求会不断归还计数，因而不能把 30 讲成每分钟配额。

**面试怎么说**：我用自定义注解和 AOP 把登录接口的并发保护放在业务方法外层。切面按 IP 和接口在当前实例内计数，尽量挡住同一来源同时打进来的大量请求。复盘时也发现，超限分支在 `try/finally` 前抛出，拒绝请求增加的计数缺少对应回退，且定时清表会打断正在进行的计数。因此我会把它讲成单实例的并发保护及其待完善点。
